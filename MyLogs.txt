PROJECT LOG

Project goal
This project is for a low altitude drone that flies in cities at about truck height.
The drone needs to understand what is around it so it can avoid objects safely.
The first phase of the project is to build a semantic segmentation model using the Cityscapes fine annotation dataset.

Dataset Selection Rationale
The following datasets were evaluated during the planning phase:
- CarObjectDetection: Rejected. Images are primarily side-profiles of cars. A navigating drone requires a forward-facing (ego-centric) perspective to detect obstacles in its actual flight path.
- ZurichDataset: Rejected. Despite being drone-based, the camera angles point at rooftops and homes rather than the forward path needed for low-altitude obstacle avoidance.
- COCO (Common Objects in Context): Rejected. A massive, general-purpose dataset with too many irrelevant classes (e.g., animals, indoor furniture). Wastes neural network capacity for an edge model.
- Pascal VOC 2012: Rejected. Highly focused on everyday household objects and close-ups, offering no structural value for urban road navigation.
- VisDrone: Rejected for Phase 1. Features a high-altitude, bird's-eye view, unlike our low-altitude "truck height" requirement. (Will be reconsidered for Phase 2 top-down target tracking).
- Cityscapes: Selected. Recorded from vehicle dashcams, perfectly matching our drone's forward-facing, low-altitude perspective. Crucially, it provides highly accurate pixel-level semantic segmentation for 19 urban classes, allowing the flight controller to explicitly calculate "free space" (roads) versus boundaries.

Model Selection Rationale
The following architectures were selected to evaluate the trade-off between standard segmentation accuracy and real-time edge latency:

1. The Baseline: FCN-ResNet50 (Fully Convolutional Network)
- What it is: A classic, battle-tested semantic segmentation architecture built natively into PyTorch.
- Why it was chosen: Selected to establish a reliable benchmark. It represents the traditional, unoptimized approach to segmentation. It answers the question: "What is the standard latency if we don't optimize for drones?" (Benchmarked at ~39.60 ms, which is too slow for our real-time requirements).

2. The Edge Model: YOLOv8n-seg (YOLOv8 Nano Segmentation)
- What it is: An ultra-lightweight, state-of-the-art instance segmentation model designed for real-time edge computing.
- Why it was chosen: A low-altitude drone runs on a battery-powered edge computer with a strict 30 ms latency budget. The "Nano" architecture was explicitly chosen to prioritize blazing-fast inference speed over maximum accuracy. It achieved ~13.84 ms latency (nearly 3x faster than the baseline). This ensures the drone can process frames at ~70 FPS, allowing the flight controller to calculate "free space" and react to sudden obstacles in real-time.

Phase 2 — Baseline FCN-ResNet50 (completed 2026-05-14)
Source files: `src/cityscapes_dataset.py`, `src/metrics_logger.py`, `src/train_baseline.py`

Training configuration (matched to YOLO for fair comparison):
- Model: FCN-ResNet50 (pretrained=False, 19 classes)
- Train subset: 400 images
- Val subset: 400 images
- Input size: 512x512
- Batch size: 4
- Epochs: 5
- Optimizer: SGD (lr=1e-3, momentum=0.9, weight_decay=1e-4)
- Loss: CrossEntropyLoss (ignore_index=255)
- Run number: 3

Results:
- Final val mIoU: 0.3329
- Average inference latency (100 val images, GPU-sync'd forward-pass only): 39.60 ms
- Total training time: 278.25 seconds
- Checkpoints: `runs/phase2_baseline_run3/resnet50_Run3_Epoch{1-5}.pth`

Latency measurement methodology:
- Image loaded and preprocessed OUTSIDE the timed window.
- `torch.cuda.synchronize()` called before and after the model forward pass.
- Latency = net GPU forward-pass time only (no I/O, no pre/post processing).

Phase 3 — YOLOv8-Seg Edge Model (completed 2026-05-14)
Source files:
  - `src/yolo_cityscapes_utils.py` — Cityscapes label helpers and polygon normalization
  - `src/prepare_yolo_cityscapes.py` — converts JSON polygons to YOLO .txt format
  - `src/train_yolo.py` — YOLO training entrypoint and CSV logging
  - `src/append_yolo_metrics.py` — maps Ultralytics results.csv into the shared CSV
  - `src/trim_yolo_dataset.py` — trims the YOLO dataset to a fixed sample count
  - `src/yolo_latency_fixed.py` — correct GPU-sync'd latency benchmark (no NMS)
  - `src/visual_grid.py` — generates 1x4 comparison grid (Raw, GT, ResNet50, YOLO)
  - `cityscapes_trimmed.yaml` — YOLO dataset config for 400-sample trimmed subset

Training configuration (matched to ResNet50 for fair comparison):
- Model: yolov8n-seg.pt (Nano, instance segmentation)
- Train subset: 400 images (via yolo_cityscapes_trimmed)
- Val subset: 250 images (the exact first half of the 500-image val set)
- Input size: 512x512
- Batch size: 4
- Epochs: 5
- Device: GPU (RTX 3060)

YOLO dataset structure:
- Images are explicitly copied to `yolo_cityscapes_trimmed/images` and `yolo_cityscapes/images` rather than using Windows directory junctions. This prevents YOLOv8 from resolving junction paths back to the original root and failing to locate the corresponding labels.
- `labels/train` and `val` contain the generated YOLO polygon .txt files.

Results:
- Val Mask mAP50 (Epoch 1 → Epoch 5): 0.0641 → 0.1051
- Weights: `runs/segment/runs/segment/train_trimmed/weights/best.pt`

Latency measurement methodology:
- Images loaded and preprocessed OUTSIDE the timed window.
- `model.model(tensor)` called (raw PyTorch backbone, NO NMS, NO Ultralytics wrapper).
- `torch.cuda.synchronize()` called before and after the forward pass.
- 5 GPU warm-up passes run before measurement begins.
- This matches the ResNet50 measurement methodology exactly for a fair comparison.

Latency results (100 validation images, GPU-sync'd forward-pass only):
- YOLOv8n-seg: 10.87 ms
- FCN-ResNet50: 34.27 ms
- Comparison: YOLO is 3.15x faster than ResNet50.
